# Commercial E2E Readiness And Implementation Order

Date: 2026-05-07

Purpose: define the single end-to-end launch contract for the Pilates SaaS landing funnel, connecting Spec 1 Landing, Spec 2 Atendente IA, Spec 3 Billing and Spec 4 Onboarding.

This file is the cross-spec checklist used before implementing and before declaring the commercial landing ready.

Operational companions for Spec 1 and Spec 2:

- [commercial-e2e-qa-checklist.md](./commercial-e2e-qa-checklist.md): practical QA script for landing, consultor, WhatsApp, Sales Inbox and optional n8n alerts.
- [commercial-runtime-env-map.md](./commercial-runtime-env-map.md): environment variables and external credentials map.
- [commercial-operator-runbook.md](./commercial-operator-runbook.md): how to operate SaaS sales leads before the real SaaS/billing/onboarding specs are finalized.

## 1. Expected End State

At launch, the Pilates landing is not only a marketing page. It is a complete assisted-sales funnel:

1. Visitor arrives at `/pilates`.
2. Visitor understands the SaaS promise, pains, agents and proof.
3. Visitor enters through widget, Falar com consultor, Continuar no WhatsApp, guided demo, the custom-agent diagnostic report block or the final FAQ doubt CTA.
4. The same commercial agent brain answers doubts, diagnoses pain and recommends the next step.
5. The visitor may reach `/pilates/planos`, WhatsApp assisted close, guided demo, custom-agent proposal follow-up or checkout according to readiness.
6. Checkout is created only from trusted server-side billing after a valid checkout gate.
7. Payment confirmation creates entitlement and pending tenant activation.
8. Onboarding starts only after trusted paid confirmation.
9. Every commercial lead is visible to the operator in the Sales Inbox/Postgres; optional n8n alerts are secondary.

## 2. Non-Negotiable Go-Live Definition Of Done

The landing funnel is not launch-ready unless all items below are true.

- `/pilates` has no dead CTA, no 404 destination and no cold visitor default path directly to checkout.
- `/pilates/planos` exists, uses trusted plan configuration and shows Base, 1 Agente, 3 Agentes and 7 Agentes with 7 Agentes as the recommended/default plan.
- `/pilates/demonstracao` is available only when the real SaaS demo environment supports the shown workflows. If `guidedDemoReady=false`, all demo CTAs route to consultor/WhatsApp/product explanation instead of a fake demo page.
- Widget, Falar com consultor, Continuar no WhatsApp, guided demo and FAQ doubt CTA entry paths preserve entry metadata and start with the correct tone.
- The Agente sob medida diagnostic block generates a structured report, classifies mapped/custom/mixed/unclear requests and carries diagnostic context into consultor, guided demo or WhatsApp CTAs.
- The FAQ keeps at most 8 high-impact questions and ends with a "ficou alguma duvida?" CTA that opens the normal widget-style consultor with `sourceSection=faq_doubt_cta`.
- The Atendente IA answers purchase-relevant questions from trusted configuration plus approved answer knowledge before steering the visitor back to conversion.
- Plan display gates and checkout gates are enforced in UI, agent response metadata and billing route validation.
- The 30-day guarantee is visible or reachable before checkout in landing, Atendente IA answers and billing terms.
- Payment data is never collected by landing, chat, WhatsApp, n8n or Sales Inbox.
- Checkout is created server-side using Asaas credentials and trusted plan configuration.
- Active entitlement and onboarding access are granted only after trusted paid/received webhook confirmation.
- Sales Inbox exists before claiming same-number human takeover on WhatsApp.
- Every lead from widget, WhatsApp, guided-demo intent/completion, plans-page intent, checkout intent, human handoff, custom-agent request and custom-agent diagnostic report CTA/result is visible in the Sales Inbox.
- Widget and WhatsApp activity for the same buyer can merge into one lead only through strong identifiers: explicit `leadId`, WhatsApp number/provider contact, email or explicit session linkage.
- n8n failures do not block chat, WhatsApp replies, operator control, checkout or onboarding.
- Evals cover pricing, 7 Agentes recommendation, lower-plan objection handling, unsupported questions, demo gating, checkout gates, WhatsApp opt-out, human takeover and lead merge behavior.

## 3. Lead Identity And Merge Rules

The product must treat lead identity as a first-class E2E concern.

Strong identifiers allowed for automatic merge:

- explicit `leadId`;
- WhatsApp provider contact ID;
- normalized WhatsApp number;
- verified or explicitly provided email;
- explicit session continuation token generated by the system.

Weak identifiers must not auto-merge by themselves:

- studio name;
- city/state;
- browser fingerprint;
- IP address;
- similar conversation content;
- same selected plan or same pain.

If only weak identifiers match, the Sales Inbox may show a possible duplicate for operator review.

Required shared lead metadata:

- `leadId`;
- `sessionId`;
- `channel`;
- `entryPath`;
- `sourcePage`;
- `selectedPainIds`;
- `recommendedAgentIds`;
- `interestedPlanId`;
- `recommendedPlanId`;
- `conversionPath`;
- `checkoutGateReason`;
- `guidedDemoScenario`;
- `guidedDemoCompleted`;
- `contactConsent`;
- `whatsappOptOut`;
- `safeSummary`;
- `nextAction`;
- `status`;
- `priority/readiness`.

## 4. Approved Commercial Answer Source

The Atendente IA must answer from this order:

1. trusted runtime/system configuration;
2. approved answer knowledge;
3. commercial sales playbook;
4. safe fallback or WhatsApp/Sales Inbox handoff.

The implementation must not ship public AI selling behavior until approved answers cover at least:

- what Taliya is;
- what each of the seven agents does;
- Base, 1 Agente, 3 Agentes and 7 Agentes differences;
- why 7 Agentes is the natural recommendation for broad needs;
- setup in a few minutes after payment confirmation;
- studio-owned WhatsApp for paying studios;
- human control/takeover;
- message hard caps and quota options;
- 30-day guarantee;
- cancellation/refund boundary;
- what happens after subscribing;
- what happens if payment fails;
- Agente sob medida as separate business;
- custom-agent diagnostic report outcomes: mapped existing solution, custom agent, mixed solution and unclear;
- unsupported integrations/features;
- privacy/payment-data safety.

## 5. Guided Demo Gate

The guided demo is a proof surface for the real SaaS, not a landing mockup.

Implementation rules:

- `guidedDemoReady=false` by default until the SaaS demo environment exists.
- If not ready, the agent may explain that the demo becomes available with the real SaaS environment and offer consultor, WhatsApp or product explanation.
- If ready, `/pilates/demonstracao` must use approved demo data and real SaaS workflows.
- The guided demo must preserve selected pain, selected agents, scenario and completed-step context when returning to consultor or plans.
- The guided demo must not route to checkout as its default final action.

## 6. Implementation Order

Recommended implementation sequence:

1. **Spec Freeze And Repair Baseline**
   Align the working tree with the approved specs, remove/finish partial drift and confirm no implementation starts from outdated plan names or conversion paths.

2. **Trusted Commercial Configuration**
   Create the shared plan/offer configuration for Landing, Atendente IA, Billing and Onboarding: plans, prices, recommended plan, guarantee, quotas, WhatsApp scope, checkout destinations and demo readiness.

3. **Landing Funnel Integration Without Redesign**
   Preserve the accepted `/pilates` layout. Only finish integration items such as CTA wiring, entry metadata, consultor-first behavior, route gates, tracking/schema alignment and responsive bug fixes. Do not redesign, reorder or restyle the main landing unless the user explicitly reopens the visual direction. Implement the Agente sob medida diagnostic block as a report generator only if it can be added without undoing the approved layout direction or after explicit approval.

4. **Plans Page**
   Implement `/pilates/planos` with configured plan cards, comparison, fit guidance, FAQ, 30-day guarantee, consultor CTA and checkout CTA placeholders/gates.

5. **Atendente IA Web**
   Implement the web agent with approved answer knowledge, commercial playbook, plan gates, checkout gates, risk-reducer answers, custom-agent diagnostic report mode, tracking and evals.

6. **Lead Store And Sales Inbox MVP**
   Build the internal lead/conversation store and protected Sales Inbox before production WhatsApp human takeover. Include list, detail, merge rules, statuses, actions and audit events.

7. **WhatsApp Channel**
   Add official Meta WhatsApp Cloud API inbound/reply support, server-side sessions, idempotency, opt-out, same-brain behavior and operator takeover.

8. **Optional n8n Automations**
   Add n8n workflows only for follow-up eligibility, daily digest and urgent notifications. Lead upsert belongs to Sales Inbox/Postgres.

9. **Billing And Checkout**
   Implement Asaas server-side checkout, checkout gates, payment webhooks, entitlement creation, payment failure denial, quota add-ons and 30-day guarantee configuration.

10. **Onboarding**
    Implement post-payment account/studio setup, entitlement-aware agent configuration, studio-owned WhatsApp setup status and safe commercial-context prefill.

11. **Guided Real SaaS Demo**
    Build `/pilates/demonstracao` only after the SaaS demo environment exists, using real workflows and approved demo data.

12. **E2E Launch Verification**
    Run full funnel tests from all entry paths through lead visibility, WhatsApp, plans, checkout, payment confirmation, onboarding and operator follow-up.

## 7. Protected Landing Layout Guardrail

The `/pilates` page visual/layout pass is complete and protected.

Future implementation should avoid editing these files for visual reasons:

- `app/globals.css`;
- `components/landing/NicheLandingPage.tsx`;
- `components/landing/sections/*` used by `/pilates`;
- shared visual components used directly by `/pilates`;
- `data/landing/niches/pilates.ts` copy/section data when the change would alter the approved visual narrative.

Allowed `/pilates` changes are limited to:

- CTA wiring;
- entry metadata;
- tracking/event payloads;
- schema/config alignment;
- guided-demo and checkout route gates;
- accessibility fixes;
- responsive overflow or broken-state bug fixes;
- explicit user-requested visual changes.

This thread may continue with lower-conflict work:

- `/pilates/planos`;
- Atendente IA behavior, prompts, schemas and evals;
- commercial configuration contracts;
- tracking/event contracts;
- lead store and Sales Inbox planning/implementation;
- billing/onboarding specs and server-side contracts.

Before launch, revisit only the landing integration points:

- hero/header/final CTA behavior;
- custom-agent diagnostic report CTA behavior;
- consultor-first entry metadata;
- demo CTA gating while `guidedDemoReady=false`;
- plan-comparison routing;
- WhatsApp handoff copy;
- high-ticket risk reducers before checkout;
- responsive screenshots and no-overflow checks.

## 8. Launch Blockers

Any one of these blocks public launch:

- `/pilates/planos` missing while any path links to it.
- `guidedDemoReady=true` without a real SaaS demo environment.
- checkout offered from a cold landing CTA without a valid gate.
- Sales Inbox missing while WhatsApp human takeover is promised.
- lead records not visible to the operator.
- payment success inferred from redirect/query string instead of webhook.
- onboarding accessible from chat intent, lead status or unpaid checkout state.
- plan/pricing duplicated in prompt/component text instead of trusted configuration.
- guarantee/cancellation terms absent from landing/agent/billing surfaces.
